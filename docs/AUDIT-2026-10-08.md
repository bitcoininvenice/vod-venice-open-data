### Nuove evidenze emerse durante l'implementazione
- `previsione.json` su dati.venezia.it viene servita **in modo alternato** in una versione aggiornata e in una ferma al 21/09/2026 (last-modified 21 Sep): probabile nodo di cache non sincronizzato lato Comune. La UI mostra sempre la data di emissione e segnala la previsione vecchia.

- La quota anonima di OpenSky si esaurisce rapidamente da un IP condiviso (HTTP 429 già in sviluppo): in produzione su Vercel servono le credenziali OAuth2.

## 1. Executive Summary

1. **Il problema principale è l'integrità dei dati, non il codice.** Su 27 route API solo 2 contattano una fonte esterna (`/api/flights` → OpenSky, `/api/cameras/snapshot` → SkylineWebcams). Tutte le altre restituiscono costanti hardcoded con `timestamp: new Date()`, presentate in UI come "live", "tempo reale", "certificato", "ufficiale".
2. **Dati fabbricati attribuiti a enti reali.** Il METAR LIPZ è generato con valori fissi (060°/12 kt, 18/12, Q1016) e attribuito ad Aeronautica Militare/ENAV; oggi il METAR reale era `04007KT 6000 -RA 18/17 Q1012`. La marea è fissa a 76 cm "CPSM"; il valore reale a Punta Salute era 17 cm. I 12 cantieri `VE-CANT-2026-xx` non provengono da dati.venezia.it. Rischio reputazionale e legale concreto.
3. **Le fonti reali esistono e funzionano**: `livello.json`/`previsione.json` del Comune, GTFS-RT ACTV (nav + aut, protobuf con posizioni vere), GTFS statici ACTV, METAR da aviationweather.gov. Il progetto non li usa.
4. **PostgreSQL/PostGIS non è collegato all'app**: `web/` non ha il driver `pg`, `lib/db.ts` è un file di costanti. La pipeline inserisce dati hardcoded (`import_comune_venezia.py`), scarta il feed GTFS-RT reale (`sync_gtfs_rt.py:129`) e `export_simulation_data.py` è uno stub: `simulation-data.ts` (2,3 MB) non è rigenerabile.
5. **Sicurezza**: nessun header di sicurezza, nessun rate limiting, proxy snapshot che falsifica `Referer`/`User-Agent` per aggirare l'hotlink protection di SkylineWebcams, nessun lockfile (build non riproducibili, `npm audit` impossibile), password DB loggata in chiaro dalla pipeline.
6. **Architettura frontend**: `MapEngine.tsx` 4.899 righe con un unico `useEffect` di rendering con ~100 dipendenze che ricrea il loop rAF a ogni cambio di stato e disegna a 60 fps anche da fermo; `page.tsx` con 116 `useState`; 12 modali senza shell comune né `role="dialog"`/Escape; 7 bug di contratto client↔API (dati API mai applicati).
7. **Zero test**, lint rotto (`next lint` rimosso in Next 16, nessuna config ESLint).

**Priorità assoluta**: (a) etichettare onestamente o rimuovere i dati fittizi; (b) collegare le 4 fonti reali già verificate; (c) hardening proxy + header + lockfile.

## 3. Architettura e qualità del codice

### 3.1 Struttura reale vs dichiarata

```
Dichiarato:  Fonti → pipeline Python → PostGIS → API Next → client
Reale:       costanti TS ──┬──> import diretto nel bundle client (page.tsx)
                           └──> API route che ri-serializzano le stesse costanti
             PostGIS + pipeline: isolati, mai letti dall'app
```

Ogni dataset è quindi **spedito due volte** (nel JS client e via API) e le API sono di fatto decorative.

### 3.2 Problemi principali

| Problema | Dove | Perché conta | Come correggere |

## 4. Revisione del codice: aree critiche

1. **Server vs client component**: `app/page.tsx` è interamente `'use client'` e importa tutti i dataset. Rendere `page.tsx` server component che carica i dati iniziali (cache `revalidate`) e passa solo ciò che serve a un `<MapShell>` client; `MapEngine` caricato con `next/dynamic` `ssr:false`.
2. **Polling inutile**: `/api/alilaguna` ogni 8 s (`page.tsx:498`) restituisce rotte/fermate statiche, mentre le barche sono già calcolate client-side con `getScheduledAlilagunaBoats`. Eliminare il polling.
3. **Errori**: tutte le route fanno `catch (error: any) → error.message` al client (leak di dettagli interni). `flights/route.ts` ingoia ogni errore senza log. Standardizzare: `{ ok, data, meta: { source, fetchedAt, stale } }` + log strutturato server-side.
4. **Input non validati**: `spatial/stops-near-cantieri` accetta `radius` arbitrario (`NaN`, `1e9` → O(n·m) senza limite); `stops?mode=` libero. Validare con Zod (snippet §9.4).
5. **Timeout**: `cameras/snapshot` fa `fetch` senza timeout; `flights` usa `AbortController` ma combina `next.revalidate` con `force-dynamic` (la cache non si applica). Usare `AbortSignal.timeout(4000)` e una cache esplicita.
6. **Time zone**: `realtime/vehicles` usa `now.getHours()` (UTC su Vercel) mentre `alilaguna` usa correttamente `Europe/Rome`. Centralizzare in `lib/time.ts`.
7. **Codice morto**: `/api/realtime/vehicles` (non chiamato), `fetchSatellites/fetchPasserelle/fetchMarineSensors/fetchVeniceAssets` in `db.ts` (non usate dal client), `INITIAL_LIPZ_METAR`, alias `MOCK_STOPS`/`VERIFIED_CANTIERI_DATA`, campo `cctvSurveillance` dopo il rename terminologico, `db/02_spatial_queries.sql` mai invocato dall'app.
8. **Commenti**: molti commenti promozionali ("Fallback ad alta fedeltà", "Gemello digitale deterministico", "certificate") descrivono intenzioni non vere. Sostituire con commenti che spiegano provenienza e limiti del dato.
9. **Naming**: mix italiano/inglese nello stesso tipo (`livelloCm`, `tendenza` accanto a `stations`, `moseGates`). Scegliere inglese per il codice, italiano solo per stringhe UI.

## 5. Sicurezza (ordinata per gravità)

L'app è pubblica e read-only senza autenticazione: corretto per un portale open data, purché non esistano endpoint di scrittura (oggi non ne esistono).

| # | Gravità | Vulnerabilità | Dove | Fix |
|---|---|---|---|---|
| 1 | **Alta** | Proxy che aggira l'hotlink protection (spoofing `Referer`/`User-Agent`) e redistribuisce immagini proprietarie; nessun rate limit → banda/costi Vercel sfruttabili; segue redirect upstream | `api/cameras/snapshot/route.ts:27-34` | Rimuovere. Se autorizzati: solo `id` (niente `url`), `redirect: 'error'`, timeout, limite dimensione, cache CDN `s-maxage=30`, rate limit |
| 2 | **Alta** | Nessun lockfile committato | repo | `npm install` → committare `package-lock.json`; `npm ci` in CI; `npm audit` + Dependabot/Renovate. Senza lockfile non è possibile garantire di non ricevere versioni compromesse (supply chain) |
| 3 | **Alta** | Nessun header di sicurezza (CSP, HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, frame-ancestors) | `next.config.ts` | Snippet §9.1 |
| 4 | Media | Nessun rate limiting su nessuna route; `/api/flights` consuma quota OpenSky condivisa a ogni richiesta | tutte | Vercel Firewall rate-limit rule o `@upstash/ratelimit`; cache server condivisa per le fonti upstream |
| 5 | Media | Credenziali DB loggate in chiaro | `pipeline/import_gtfs.py:29` (`{DATABASE_URL}` nel log) | Loggare solo host/db; mai l'URL completo |
| 6 | Media | Credenziali di default `vod_user/vod_password` hardcoded in `docker-compose.yml` e come default negli script Python; Postgres esposto su `0.0.0.0:5432` | `docker-compose.yml`, `pipeline/*.py` | `env_file`, nessun default nel codice (fallire se manca), `ports: "127.0.0.1:5432:5432"` |
| 7 | Media | Leak di `error.message` nelle risposte 500 | `stops`, `stats`, `cantieri`, `spatial` | Messaggio generico + log server |
| 8 | Media | DoS algoritmico: `radius` non limitato | `api/spatial/stops-near-cantieri` | Clamp 10–2000 m, validazione |
| 9 | Bassa | Google Fonts caricato via `@import` CSS da `fonts.googleapis.com` | `globals.css` | `next/font/google` (self-hosting): elimina trasferimento IP a Google (GDPR) e richiesta bloccante |
| 10 | Bassa | Download GTFS su `http://` | `.env.example`, `pipeline/download_gtfs.py` | `https://` + verifica checksum/dimensione e `zipfile` con controllo path traversal (`..`) prima dell'estrazione |
| 11 | Bassa | Nessun logging/monitoring strutturato | — | Vercel Log Drains o Sentry; metriche per fonte (latenza, errori, staleness) |
| 12 | Info | Next 16.1.1 / React 19.2.3: verificare advisory correnti dopo aver generato il lockfile (`npm audit`); nel 2025 sono stati pubblicati più advisory su React Server Components/Next | `web/package.json` | Allineare all'ultima patch 16.x |

**SQL injection**: lato web non esiste SQL. La pipeline usa query parametrizzate (`execute_values`, `%s`); l'EWKT è costruito con f-string da float parsati dal CSV: convertire esplicitamente con `float()` prima dell'interpolazione o usare `ST_SetSRID(ST_MakePoint(%s,%s),4326)`.
**XSS**: nessun `dangerouslySetInnerHTML`/`innerHTML`; React fa escaping. Quando si introdurranno dati esterni (nomi stazioni, headsign GTFS) restano sicuri finché passano da JSX; nel canvas `fillText` non è un sink XSS.
**CSRF**: non applicabile (solo GET, nessuna sessione).
**Sicurezza DB** (quando collegato): ruolo applicativo read-only (`GRANT SELECT`), ruolo pipeline separato, `sslmode=require`, nessun superuser per l'app.

**Chiarezza ufficiale vs collaborativo vs simulato** (il punto UX più importante): introdurre un campo obbligatorio di provenienza per ogni layer e mostrarlo come badge in LayerPanel, popup e modali:

Interventi: `<Modal>` condiviso; lista accessibile degli elementi visibili (tabella/elenco sincronizzato col viewport); `aria-pressed` sui toggle; contrasto colori dei layer verificato (molti testi canvas 8 px: `font: bold 8px "DM Mono"` è sotto la soglia di leggibilità); `prefers-reduced-motion` per fermare le animazioni.

**Responsive**: preset camera già differenziano mobile/desktop; il calcolo usa `window.innerWidth < 640` nel render → spostare in un hook `useMediaQuery`.

**Documentazione**: README e `/layers` descrivono un'architettura (PostGIS, GTFS-RT, API live) che non è quella in esecuzione. Aggiornare con: architettura reale, tabella fonti (quella di §2), come rigenerare i dataset, licenze e attribuzioni (pagina `/credits` obbligatoria per CC BY/ODbL).

**Scalabilità**: per gli attuali volumi non serve PostGIS a runtime. Decidere esplicitamente:
- Opzione A (consigliata ora): niente DB in produzione; pipeline → file statici (GeoJSON/FlatGeobuf/PMTiles) su CDN; route live con cache. Costi minimi, nessuna superficie DB.

```ts
// web/src/server/upstream.ts
import 'server-only';

export type Upstream<T> =
  | { ok: true; data: T; fetchedAt: string }
  | { ok: false; error: string };

export async function fetchUpstream<T>(
  url: string,
  parse: (raw: unknown) => T,
  { revalidate = 60, timeoutMs = 5000 } = {},
): Promise<Upstream<T>> {
  try {
    const res = await fetch(url, {
      signal: AbortSignal.timeout(timeoutMs),
      next: { revalidate },
      headers: { 'User-Agent': 'VOD-VeniceOpenData/1.0 (+https://venice-open-data.vercel.app)' },
    });
    if (!res.ok) return { ok: false, error: `HTTP ${res.status}` };
    return { ok: true, data: parse(await res.json()), fetchedAt: new Date().toISOString() };
  } catch (e) {
    console.error('[upstream]', url, e instanceof Error ? e.message : e);
    return { ok: false, error: 'upstream_unavailable' };
  }
}
```

### 9.3 GTFS-RT ACTV lato server

```ts
// web/src/app/api/realtime/vehicles/route.ts
import { NextResponse } from 'next/server';
import GtfsRealtimeBindings from 'gtfs-realtime-bindings';

export const revalidate = 20;
const FEEDS = {
  nav: 'https://tpl.actv.it/nav/GTFSRT/vehiclePositions',
  aut: 'https://tpl.actv.it/aut/GTFSRT/vehiclePositions',
} as const;

async function load(url: string) {
  const res = await fetch(url, { signal: AbortSignal.timeout(5000), next: { revalidate: 20 } });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const feed = GtfsRealtimeBindings.transit_realtime.FeedMessage.decode(new Uint8Array(await res.arrayBuffer()));
  return feed.entity.flatMap(e => {
    const v = e.vehicle;
    if (!v?.position) return [];
    return [{
      id: v.vehicle?.id ?? e.id,
      tripId: v.trip?.tripId ?? null,
      lat: v.position.latitude,
      lon: v.position.longitude,
      bearing: v.position.bearing ?? null,
      timestamp: Number(v.timestamp ?? 0),
    }];
  });
}

export async function GET() {
  const results = await Promise.allSettled([load(FEEDS.nav), load(FEEDS.aut)]);
  const [nav, aut] = results.map(r => (r.status === 'fulfilled' ? r.value : null));
  return NextResponse.json({
    ok: nav !== null || aut !== null,
    data: { nav, aut },
    meta: { kind: 'live', source: { name: 'ACTV / AVM GTFS-RT', url: 'https://tpl.actv.it' } },
  });
}
```
